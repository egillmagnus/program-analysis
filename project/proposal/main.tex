\paragraph{Context} 
In an increasingly digitized world, developers want to be able to trust that their programs do not contain issues or security vulnerabilities. One tool for battling these problems is abstract interpretation, which can be used to effectively find such issues. However, this poses the question; Can we trust the tool to correctly analyze the programs? 


\newcommand\step{\to}
\newcommand\stepa{\triangleright}

% What is a an abstract interpereter.
An abstraction $(\sqsubseteq_A, A)$ is a partially ordered set that has a Galois-connection to the set of states of a program, $\Sigma$. A Galois-connection consists of two mappings between the abstract to the concrete domain, the \emph{abstraction} $\alpha: 2^\Sigma \to A$ and the \emph{concretion} $\gamma: A \to 2^\Sigma$, for which it must hold, for any $c \in 2^\Sigma$ and $a \in A$:
$$c \subseteq \gamma(a) \iff \alpha(c) \sqsubseteq_A a$$
The goal of an over-approximating abstract interpreter is to interpret the program 
$p$ in the abstract domain using an abstract stepping function  $\stepa$, such that it over-approximates the concrete stepping function $\step$. Concretely, if we can evaluate (step many times $\stepa^*$) the abstraction of the initial states $I_p$ to an abstraction $a$, we are given that there exists no concrete evaluation from an initial state that ends in a state outside of $\gamma(a)$:
\begin{align}
p \vdash \alpha(I_p) \stepa^* a
\implies
\neg
\exists \sigma_0 \in I_p, 
\sigma' \not\in \gamma(a).\
p \vdash \sigma_0 \step^* \sigma'
\end{align}
This is a useful property as it lets us infer that all behaviors not witnessed in the abstract domain are impossible in the concrete. E.g., if we do not see a security vulnerability in the abstract, we are sure that it does not exist in the concrete.

\begin{lstlisting}[float, label=lst:concrete, caption=Concrete Step of Binary opr]
def stepBinary (opr: String) (s : State) : Err State := do
    let frame <- ConcreteFrame.topframe s
    let ([v1, v2], frame') <- frame.unstack 2
    let v <- concreteArithmetic opr v1 v2
    let frame'' <- ConcreteFrame.push v
    let frame''' <- ConcreteFrame.incrpc frame''
    s.updateFrame s frame'''
\end{lstlisting}

\begin{lstlisting}[float,label=lst:abstract,caption=Abstract Step of Binary opr]
def stepAbstractBinary (opr: String) (s : AbstractState) : Err AbstractState := do
    let abstractframe <- AbstractState.topframe s
    let ([v1, v2], aframe') <- AbstractState.unstack abstractframe 2
    let v <- abstractArithmetic opr v1 v2 
    let aframe''  <- AbstractFrame.push aframe'  
    let aframe'''  <- AbstractFrame.incrpc aframe''
    AbstractState.updateFrame s aframe'''
\end{lstlisting}

\paragraph{Gap}
To verify an over-approximating abstract interpreter, we need both a concrete and an abstract interpreter and to show that the latter correctly approximates the former.
When proving the that break it down, so we only have to prove one step at a time.
\begin{align}
p \vdash a \stepa a'
\implies
\neg
\exists \sigma \in \gamma(a), 
\sigma' \not\in \gamma(a').\
p \vdash \sigma \step \sigma'
\end{align}
In \cref{lst:concrete,lst:abstract}, we have listed the concrete and abstract implementations of the stepping function for \textit{binary}.
It is not immediately evident from an implementation whether the stepping in the concrete and abstract domain satisfy these rules.
Although they look the same, we still need to prove order preservation between every function used. This means that  \textit{AbstractFrame.push} should over-approximate \textit{ConcreteFrame.push}, 
\textit{AbstractState.topframe} should over-approximate \textit{State.topframe}, 
and so on.
This is a lot of boilerplate, when only the 
proof that \textit{abstractArithmetic} is over-approximating 
\textit{concreteArithmetic} is truly interesting.
To make matters worse it should be noted that a proof is needed for each and every instruction.  As such, it is both difficult and tedious to prove that every abstract step correctly over-approximates the concrete step functions. Doing this for all step functions is not very scalable.


\paragraph{Innovation}
In this project, we set out to build a framework for building verified abstract interpreters in Lean4~\citep{LeanLang}.  
To do this, we set out to implement a generic interpreter,
an interpreter which is both concrete an abstract. 
This can automate a lot of the proving conditioned on some typeclass requirements on the implementation of abstractions. In this way, the amount of overhead for adding a new abstraction is greatly reduced. All of the proving will be done using Lean4's theorem proving capabilities, to further decrease the overhead and give a high level of confidence in the proofs.

\paragraph{Evaluation}
To evaluate our idea, we will instantiate our framework on a subset of the JVM, and benchmark it against the JPAMB suite. The aim is to be able to handle the simple cases of the benchmark suite. 
Then we are going to formally verify and compose different abstractions including showing termination of widening operators, to show that our framework is compositional.

Finally, we will compare our approach with those of other efforts in the realm of verified compilers, such as CompCert and CakeML. The majority of these efforts use theorem provers such as Rocq, Isabelle/HOL and HOL4.
